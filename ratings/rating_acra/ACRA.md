Аналитическое Кредитное Рейтинговое Агентство (АКРА)
https://www.acra-ratings.ru/press-releases/

## Источник

Обычный server-side Bitrix: HTML отдаётся целиком, ни JS, ни публичного API нет.
Требуется браузерный `User-Agent` (см. `config.USER_AGENT`).

Листинг: `/press-releases/?types[0]=6&count=30`

- `types[0]=6` — только «Пресс-релиз» (см. раздел о прочих типах ниже).
- `count` принимает лишь 10/20/30; значения больше молча схлопываются в 30.
- Глубже 30 позиций — пагинация `?PAGEN_1=N`; сейчас не используется, одной
  страницы хватает с запасом (АКРА публикует ~5–15 релизов в день).
- Сортировка по умолчанию — по дате, новейшие сверху.

## TLS: сайт отдаёт неполную цепочку сертификатов

`acra-ratings.ru` присылает только листовой сертификат, без промежуточного
`GlobalSign RSA OV SSL CA 2018`. Браузеры и curl дотягивают его по AIA-ссылке,
Python — нет, поэтому обычный запрос падает с `CERTIFICATE_VERIFY_FAILED`.
Промежуточный сертификат лежит рядом в `globalsign_rsa_ov_ssl_ca_2018.pem` и
подмешивается в SSL-контекст в `client._build_ssl_context()`.
**Срок действия файла — до 21.11.2028**, после чего его нужно обновить:

```
curl -o gs.crt http://secure.globalsign.com/cacert/gsrsaovsslca2018.crt
openssl x509 -inform DER -in gs.crt -out globalsign_rsa_ov_ssl_ca_2018.pem
```

## Селекторы

Строка листинга:

```html
<div class="documents-row">
  <div class="documents-row__item" data-type="name">
    <span class="item__emit">ПАО СБЕРБАНК</span>          <!-- имя эмитента -->
    <a class="item__title" href="/press-releases/7142/">АКРА ОТОЗВАЛО …</a>
  </div>
  <div class="documents-row__item" data-type="sector">Кредитные организации</div>
  <div class="documents-row__item" data-type="type">Пресс-релиз</div>
  <div class="documents-row__item" data-type="date">4 авг 2026</div>
</div>
```

`uid` — числовой id из href. Сигнала изменения релиза у АКРА нет, поэтому
`ReleaseStub.modified` не заполняется и дедуп идёт по одному `uid` (как у НКР).

Имя эмитента из `span.item__emit` — самое чистое (`САО "ВСК"`, `ПАО СБЕРБАНК`),
поэтому оно переносится на детальную страницу через `ReleaseStub.entity_name`.
На самой странице краткого имени может не быть, а полное бывает вида
`LIDOIL FZCO (ЛИДОЙЛ ФЗКО) / Общество с ограниченной ответственностью «Лид Капитал»`.

Страница релиза `/press-releases/{id}/`:

- `h1.caption-block.page-caption` — заголовок;
- `time.publication_date[datetime="03.08.2026 15:50:10"]` — дата публикации;
- `div.current-document__inner-content` — тело релиза. **Парсим только его:**
  в блоке `.aside` лежат связанные документы, их ISIN не должны попасть в событие;
- в хвосте тела — таблицы «Регуляторное раскрытие», откуда берутся
  «Краткое/Полное наименование…», «Вид объекта рейтинга» и **ИНН**.

ИНН есть у всех корпоративных релизов, включая релизы уровня эмитента без ISIN —
это важно, матчинг на портфели (`alerts._match_bonds`) идёт по ISIN **или** по
ИНН эмитента. У иностранных эмитентов рядом стоит `TIN: DMCC189689`, поэтому
регулярка требует именно метку `ИНН:`. У релизов по регионам ИНН нет вовсе
(`inn=None` — это норма, а не сбой парсинга).

## Ловушки парсинга

**1. Гомоглифы кириллица/латиница в значении рейтинга.** В заголовках вперемешку
встречаются `AAA(RU)` (лат.), `ААА(RU)` (кир.) и смешанные — `АA-(RU)`, `AAА(RU)`,
`ВВВ+(RU)`. Кириллическим бывает и префикс ожидаемого рейтинга: `еAAA(RU)`.
Без нормализации одно и то же значение попало бы в БД в нескольких вариантах,
поэтому `_VALUE_RE` принимает оба алфавита, а `_normalize_value` сводит буквы
к латинице.

**2. Несколько рейтинговых шкал:**

| Вид | Пример | Где встречается |
|---|---|---|
| национальная | `AAA(RU)` | основная масса релизов |
| структурированное финансирование | `AAA(ru.sf)` (строчными!) | ИЦБ, СФО, транши |
| ожидаемый рейтинг | `eAAA(RU)`, `еAAA(RU)` | выпуски «планируемые к выпуску» |
| суверенная | `BB-` без суффикса | рейтинги стран |

Суверенные значения без суффикса намеренно не распознаются (`rating_value=None`):
бумаг таких эмитентов в портфелях пользователей нет, а расширение регулярки
на голые буквы дало бы много ложных срабатываний.

**3. Значение не всегда есть в заголовке.** У релизов по структурированному
финансированию («ПОДТВЕРДИЛО КРЕДИТНЫЙ РЕЙТИНГ СТАРШЕГО ТРАНША…») шкала указана
только в лид-абзаце тела — отсюда фолбэк на **первое** совпадение в теле.
В самом заголовке актуальное значение, наоборот, всегда **последнее**
(«ПОВЫСИЛО … С X ДО Y»).

**4. У отзыва рейтинга нет ни значения, ни прогноза.** В теле такого релиза они
ещё упоминаются как история, поэтому при `rating_action == "Отозван"` фолбэк на
тело отключён.

**5. Имя эмитента: у релизов по регионам нет ни краткого названия, ни имени
рейтингуемого лица** — только «Полное наименование объекта рейтинга»
(`Томская область`). Оно стоит последним в цепочке фолбэков, потому что для
выпусков облигаций в это же поле попадает многословное
`Облигации, ПАО СБЕРБАНК, Старший необеспеченный долг серии: …`.
Фолбэк на текст в кавычках «…» из заголовка отдельно отсеивает слова прогноза:
в `ПРОГНОЗ «СТАБИЛЬНЫЙ»` кавычки те же, и без фильтра именем эмитента
становился «Стабильный».

**6. WAF ограничивает частоту запросов (503 и 403).** Это именно rate limit, а
не блокировка IP. Замеры на 30 детальных страницах с одного адреса:

| Режим | Результат |
|---|---|
| пачкой, concurrency 5, только `User-Agent` | 20/30, десять 503 |
| пачкой, concurrency 5, полный набор браузерных заголовков | 21/30 |
| пачкой, concurrency 2 | 20/30 |
| последовательно, пауза 3 с | **30/30** |

Заголовки и снижение параллельности не дают ничего — важен только темп, отказы
начинаются примерно после 20-го запроса подряд. Поэтому все запросы (и листинг,
и детальные страницы) идут через общий троттл `_Throttle` с интервалом
`ACRA_REQUEST_INTERVAL` (3 с), а `ACRA_CONCURRENCY` фактически перестал быть
ограничителем. В установившемся режиме за полл забирается 0–3 новых релиза, так
что пауза не заметна; первый прогон на 30 релизов занимает ~95 с.

Сверх того `fetch_release` делает `ACRA_RETRIES` попыток через следующий прокси
с паузой `ACRA_RETRY_DELAY` (6 с — 503 означает «сбавь темп»). Не добравшийся
релиз не попадает в снимок и будет перезабран на следующем прогоне.

**Осторожно с расписанием:** прогоны Cloud Run Job не должны накладываться друг
на друга — две параллельные джобы удваивают частоту запросов к АКРА и снова
упираются в лимит. Первый прогон длится ~95 с.

## Словарь заголовков

Выборка 180 релизов (6 страниц листинга): `ПОДТВЕРДИЛО` 72, `ПРИСВОИЛО` 49,
`ОТОЗВАЛО` 38, `ПОВЫСИЛО` 11, `ПОНИЗИЛО` 10. Дополнительно в `_ACTION_STEMS`
заложены `ИЗМЕН*`, `УСТАНОВ*`, `ПЕРЕСМОТР*` — в выборку не попали, но АКРА
такие релизы выпускает (изменение прогноза, статус «рейтинг на пересмотре»).

Прогноз в заголовке — заглавными в кавычках: `ПРОГНОЗ «СТАБИЛЬНЫЙ»`.

## Прочие типы документов (сейчас не мониторим)

Листинг без фильтра отдаёт ещё два типа. Рейтингового действия в них нет, в
модель `RatingEvent` они не ложатся, но как источник данных могут пригодиться:

- **«Полный отчет» (`types[]=7`)** — развёрнутое обоснование рейтинга:
  финансовые показатели, оценки по факторам, ключевые допущения. Публикуется
  вместе с рейтинговым действием и дублирует его по сути. Потенциальная польза —
  не алерты, а аналитика: саммари по эмитенту, объяснение «почему такой рейтинг»,
  извлечение факторных оценок для сравнения эмитентов между собой.

- **«Мониторинговый отчет» (`types[]=11`)** — промежуточный контроль между
  плановыми пересмотрами. Самое ценное свойство: может фиксировать ухудшение
  или улучшение показателей **до** самого рейтингового действия, то есть
  работать как ранний сигнал о риске изменения рейтинга. Но рейтингового
  действия в нём нет, и «событием» в текущей модели он не является — под него
  нужен отдельный тип алерта («предупреждение»), а не строка в `rating_releases`.

Оба типа лежат в том же листинге и разбираются теми же селекторами — при
необходимости достаточно снять фильтр `types[0]=6` и научиться отличать их по
колонке `data-type="type"`.
